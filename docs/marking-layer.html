Price Action Mark · src/shared/marks/

The Marking Layer

Thirty-one rules that read a tape the way Al Brooks describes it — the special bars, the lines those bars form, and the entries those lines set up — plus one line of prose for every session. Rules propose candidates; the reader disposes, and only the verdicts are ever written to disk.

31rules, across three groups
6,550ES=F sessions, to 2026-08-27
965confirmed pivots
0.71marks per session, as shipped
~37 msto run every rule, once

Counts are the committed fixture in data/marks-golden.json — the same numbers npm run marks:check holds the layer to. The dataset is ES=F daily; the same rules run unchanged on the five-minute series, and the density transfers — see both bar sizes.

Everything is derived except the verdict

Detection is a pure function of (dataset, ruleConfig). It runs end to end on every load, because rule output goes stale against the candles the moment a session arrives.

marks/metrics.ts
Metrics

Per-bar columns every rule reads: body, tails, closePos, ATR, gap, roll flags.

marks/structure.ts
Structure

Pivots, legs, always-in state and the pullback count — built in one forward pass.

marks/registry.ts
Rules

One array. Push a Rule onto it and it appears in the panel, the menu, the CLI and the artifact.

marks/reading.ts
Reading

One line of prose per session, built from the marks detect() already produced — it names no pattern it did not import.

chart/marks/draw.ts
Geometry

Marks become polylines in CSS pixels. The renderer strokes them; the hit test measures the same ones.

main/marks.ts
Verdicts — stored

Keep or drop, keyed by the mark's stable id. The only part of this row that touches disk.

Everything under src/shared/marks/ is free of Node, the DOM and Svelte, so the desktop app, the published HTML artifact and the CLI report run byte-for-byte the same detection code. That is not tidiness — it is the only thing that makes a rule testable at all.

Toggling a rule does not re-detect. The full pass over 6,550 sessions is ~37 ms cold and ~15 ms once the JIT is warm; filtering an already-computed result is 0.30 ms, so a checkbox stays a checkbox rather than becoming two orders of magnitude more expensive than it looks.

The reading is hoisted the same way and for the same reason. The readout asks for one bar's reading on every crosshair move, so readingIndex() builds the date map once — 1.5 ms — and readAt() is then a pair of lookups at 0.001 ms a bar. Rebuilding that map inline was 0.65 ms per pointer event.

Three groups, in the order they depend on each other

The grouping is not filing. Entry rules import their shapes from the rules that define them — breakoutIndices from bars, findDoubles and findWedges from lines.

bars→ formlines→ set upentries

A pattern has one definition and rules that need it import it. An entry rule with its own idea of "what is a double bottom" drifts from the shape rule the first time a tolerance moves — and the chart then draws one thing and trades another.

Every row carries a sketch of its shape, drawn the way the chart draws it: candles and marks in the same tokens, the tone the rule assigns, caution dashed rather than given a fourth hue, a bar label under a bullish mark and over a bearish one — and no text at all on the geometry, because the canvas primitive draws none. Two kinds of dash appear and they mean different things: a dash in the rule's own tone is the mark's second register — an entry's stop and target rails, which the reader can switch off — while a faint grey dash is the sketch's own guide, marking a level the pattern is measured against and which the chart never draws. The prices are invented; only the shapes are the rule.

A double is drawn as the level, not as the M

It was a three-point path — first peak, neckline pivot, second peak — which traced what price did and named nothing. What the pattern is about is the one price that was tested twice and held, so the rule emits a level: the more extreme of the two peaks (their mean would leave one poking through its own line, and they sit within tolerance of each other anyway), running from the first peak to knownAt so the line does not stop short of the sessions that test it. The neckline is not lost — it is in the note, and dt-short still projects the measured move from it. The id is still built from the same two dates, so every verdict already on disk still finds its mark.

A sliding window emits the same shape several times

Wedge and triangle scan five pivots at a time, so a genuinely coiling stretch satisfies the predicate at four consecutive positions. Both keep a claimed-range list and skip overlaps; channels do the same, longest run first. Without it the count roughly doubles and the chart wears four copies of one triangle.

A trendline break is measured on the close, not the extreme

A wick through a trendline is what trendlines are for. Counting those as breaks rejects every real channel on the chart.

An entry is a band on the entry price; its stop and target are a switch

It used to draw three things at once — a filled box from entry to stop, a line at the entry, a line at the target — of which the box and the entry line said the same thing twice, and nothing was clickable but two thin rails. Now the box is the entry: a band a quarter of the risk thick, stroked as well as filled, one bar wide over the signal bar. The thickness is in price rather than pixels, so it means the same at every zoom; the width is one session because the point of entry is a session; and the dashed rails are what carry the duration, running on to where the trade resolved.

Raising the fill to make a one-bar box visible was the wrong lever, and the stroke is what replaced it: FILL_ALPHA went to 0.18 for exactly that reason and is back at 0.1 now, because the wide marks are what a flat fill number is really set by. A channel band covers about a third of the pane at the zoom a reader marks up at, and the whole of it zoomed in — measured on the shipped series: 433 channel marks, spanning 4 to 101 bars, median 6. Anything that raises it again has to answer for the wide case first.

The rails are a second register, not a second shape — a statement about the mark the reader can switch off, which is the same argument caution makes for being dashed rather than given a fourth hue. The hit test measures them too, so clicking an entry's stop finds that entry; switch them off and they are not in the shape to be found. The band's interior is a hit as well, because at a wide viewport its centre — the entry price, the exact thing the reader is aiming at — sits further from either edge than the slop allows.

Final flag cannot know it is final, and says so

Brooks names the pattern for what it turns out to be. The rule detects the causal half — a tight flag 20+ bars into a trend whose breakout closes back inside within two sessions — and leaves "was it the last one" to the outcome column. It is the best of the non-measured-move entries at +0.46R.

Two rules can contradict on the same bar

failed-bo and bo-pullback fired opposite directions on 2026-07-30: one reads the breakout as real, the other as failed. That is not a bug. The outcome column adjudicates; the tool shows both readings rather than picking one.

Density is the design constraint

A chart wearing every label is strictly less readable than one wearing none.

All 31 rules on produce 11,026 marks over 6,550 sessions — 1.68 a bar, which is unreadable by construction. The shipped defaults are budgeted to 0.71 per session, and npm run marks -- --catalogue prints the hit rate per rule so the budget is checkable rather than felt. Ten rules ship off; the twenty-one that stay on account for 4,636 of those marks.

Density is the usual reason. A rule firing on 10%+ of bars ships defaultOn: false: trend-bar at 34.5%, doji at 27.2%, shaved at 15.1% and pullback-entry at 12.3%. But it is no longer the only reason. climax fires 38 times in twenty-six years — 0.6%, nowhere near the density that hid the other four — and ships off on usage alone, the first rule to do so.

Tighten the rule before you hide it

reversal-bar went from 22% of sessions to 5.2% by requiring it to actually reverse a 10-session extreme; pin-bar from 14.2% to 3.7% by requiring the bar to be worth an ATR. Both gained meaning rather than losing coverage — hiding them would have kept the noise and only moved it.

The budget moved once since: inside and outside were switched on, taking it from 0.56 to 0.71. Both fire on about 12% of sessions — over the 10% line — and both were kept anyway, because an inside bar is a fact about the session rather than an interpretation of it, and the reading names it in prose whether the mark is drawn or not.

Two flags, and they have to move together

defaultOn is a density decision; Rule.tier is a usage one, and it decides whether the rules card lists a rule or folds it behind a +5 ▾ chip on its group heading. They mean different things — gap-bar fires 42 times and final-flag 44, so neither is off for density — but a folded rule the reader has switched on is promoted back into the list, keeping the quieter name. So tier: 'extra' on its own only makes a rule quieter; for one to actually leave the list, both flags have to move. Ten rules carry both today, and they are the same ten in each case.

Absent means core, so a rule opts in to being quiet and the other twenty-one need no line. Nothing in the marking layer reads tier: detection, the counts, --catalogue and marks:check are untouched by it. And the reader can move any rule off the tier it ships with, in a modal rules sheet that lists all 31 with a Show box, a Fold box, the outcome in words, and the density figures the card has no room for.

Bar labels are a close-up feature. Three-character labels at 11px mono are ~20px wide, so below 24px a bar adjacent labels overlap into garbage. The test is pixels per bar, not the name of a range: on daily that works out to the 1M preset and nothing wider, but 1M of five-minute bars is 6,320 of them, so intraday needs 1D or shorter before a label appears. The readout says "zoom in for bar marks" the rest of the time rather than letting them silently vanish. Geometry is not subject to that and draws at every zoom.

Structure, and the guarantee under it

Every rule reads the same pivots, so the two dials that produce them move all 31 counts at once.

Pivot strength 3

A pivot every 6.8 sessions, a median leg of 2.8 ATR over 5 bars, and always-in flipping 19× a year. Strength 2 whipsaws twice as often (17.1% of state runs last two bars or less, against 9.0%); strength 4's 7-bar legs step over swings worth marking.

Min swing 1 ATR

Near-inert above strength 2, and kept for when strength is dialled down. Both were chosen by sweeping the grid in npm run marks -- --tune, not by taste.

965 pivots

Recorded in the fixture separately from the counts, so moving a dial reports "structure dials moved" once rather than 31 failures with one cause.

Built in one forward pass, and proved rather than asserted

The alternation reduction is streaming, not a global fixed point: doing it globally would let a swing in 2012 delete a pivot from 2011, and every trend value before it would silently become a fact from the future.

--check rebuilds the whole structure from the series with its last 500 sessions removed and requires every earlier trend and pullback value to be identical. 0 of 6,050 drift. The positive control matters as much as the test: 3,981 non-zero values are compared, and a deliberate one-bar misalignment produces 456 differences.

One consequence worth knowing: pivots/legs and trend/pullback can disagree about the recent past, and that is correct. The first pair is the reading as of the last bar; the second is the causal per-bar record of what was knowable at the time.

Entries carry what actually happened

Each entry emits the three prices Brooks defines mechanically — a stop order one tick beyond the signal bar, the protective stop one tick beyond its other end, a target — and then a walk-forward result.

Four decisions in that walk are deliberately scored against the trader:

  • The order goes in at knownAt, not at the signal bar. Three rules anchor on a swing pivot, which needs three sessions to its right to confirm, so their own knownAt is three sessions later than the bar they name. See below — this one was wrong for a whole release.
  • A bar containing both stop and target is a loss. Daily OHLC cannot say which came first, and assuming the good one is how a backtest talks itself into an edge. ambiguous counts them so the number stays auditable.
  • A bar that gapped through the entry fills at the open, not the order price.
  • The entry order is live for exactly one bar. Leaving it working turns every failed setup into a different, later trade nobody took.

Measured over the whole series, the mechanical 2R target loses

DEFAULT_TARGET_R is left at 2 on purpose. Tuning it until the table looked better would be curve-fitting a review tool. The number is a finding about these setups on daily ES, and it is supposed to be visible.

The order goes in at knownAt — and for a whole release it did not

dt-short, db-long and wedge-reversal anchor on a swing pivot, which needs strength bars to its right, so their knownAt is three sessions after the signal bar they name. The walk-forward ran from the signal bar anyway. All 257 of their marks quoted the outcome of an order nobody could have placed, two sessions early.

Almost the entire edge was that head start. Measured over the whole series either side of the fix: dt-short +0.873R a mark became +0.114R, db-long +0.601R became +0.079R, and wedge-reversal +0.345R became −0.160R — which changes its sign. (Those are that run's figures; the table above is today's, on the current fixture.) An earlier version of this page quoted the first set.

trade() now takes an orderAt separate from the signal bar, and --check re-derives every entry's walk from the mark's own dates and fails if the note disagrees. Verified to have teeth: putting the walk back on the signal bar reports "wedge-reversal:2000-11-30 quotes an outcome an order placed at 2000-12-05 did not have".

Every session also gets a line of prose

The same layer that draws the marks writes the reading. It names no pattern it did not import — which is the only reason the chart and the sentence beside it cannot come to disagree.

2000-09-18 bear trend bar, first session of a new contract, so the change into it is carry — trading range 2000-09-19 bull trend bar, shaved bottom, inside the bar before — trading range — two-bar reversal 2000-09-26 bear trend bar, shaved bottom — trading range 2026-08-27 small doji, 0.5x ATR — always-in long

Three clauses: the bar itself, the context around it, and the patterns that closed on it. Only the first is coloured by the bar's direction — the other two are statements about the market around the bar, and painting them its direction would claim they agreed with it. A suspect print or a contract start is caution, which is what that tone is for.

The adjectives read BIG_ATR, DOJI_BODY, SHAVED_TAIL, PIN_TAIL and isTrendBar straight out of rules/bars.ts, and the composite patterns are not re-derived at all: the reading takes the marks detect() already produced and names them by their rule labels. A second idea of what a breakout is would drift the day BREAKOUT_LOOKBACK moved.

A mark joins a reading only if knownAt === at

A double top is not readable on the day of its second peak, and a bar-by-bar reading that names it there claims foresight. Confirmation-lagged patterns stay the tape's business, where the chip prints the date it became knowable. --check asserts it rather than trusting it: every phrase in a reading has to be a rule that fired on that bar and was knowable at its close. Verified to have teeth — dropping the filter reports "reading at 2000-10-24 names bear-channel, knowable only at 2000-10-27" and exits 1.

STATED drops the clause, never the rule

Eight rules say what an earlier clause has already said — big-bar adds nothing to a leading "big" — so they are dropped from the pattern clause. Without the set a line reads "bull trend bar, shaved top — trend bar, big trend bar, shaved bar". What survives is exactly the composite set: reversal bar, ii/ioi, climax, breakout, follow-through, two-bar reversal.

The reading is built from the unfiltered marks. A rule toggle changes what is drawn; it does not change what a bar did. Keying the prose to the enabled set would drop the "breakout" clause the moment the reader hid the arrows, which is a lie about the session.

Measured over the whole series: the longest reading is 172 characters, and 8 of 6,550 carry nothing but the bar's own body. npm run marks -- --read prints both figures, because a reading that wraps to two lines has stopped being a line.

The tape is one list, and the pattern clause is rendered as the marks

Marks in view and Bar reading were two newest-first lists over the same viewport, overlapping by construction — a reading names the patterns knowable at that close, and the mark list was listing those same patterns for the same bar. They are now one tape: a row per session, the reading as the row, and its marks as chips beside the sentence, taking the pattern clause's place. The words stop being said twice and become clickable.

Three cases fall out of that and all three are meant. A mark the prose does not name is a chip on its own — either STATED already covered it, or it was not knowable at that close, and the second kind prints the date it became knowable. A pattern the prose names with no mark behind it stays as dim text: the rule is switched off, or the mark was dropped, which is rule state made visible rather than a discrepancy papered over. A session with neither is one line of prose, which at the shipped density is a little over half of them.

The old tab became a filter — All / Marked / Unresolved — because it now asks "how much of the tape?" rather than "which list?". Unresolved counts sessions holding a mark with no verdict, so it empties as the reader works: it is the marking loop's finish line. One cap, TAPE_CAP 300, because it is one list — and the header says so, since a mark anchored older than the newest 300 sessions in view has no row to sit on.

Rules propose, the reader disposes

Click a mark on the chart to keep it, or use Keep / Drop on the tape. A dropped mark disappears from every view — keeping it visible-but-faded would mean dismissing a rule's noise never quietens the chart.

Verdicts persist to marks/<symbol>.json under the app's userData directory — ~/Library/Application Support/price-action-mark/ on macOS, %APPDATA%\price-action-mark\ on Windows — keyed by the mark's stable id. Verdicts for marks that no longer regenerate are kept, not dropped: thresholds move, and a mark that vanishes today comes back when a tolerance is loosened. They cost a few bytes, and dropping them would silently discard decisions the reader made.

Two gestures, two meanings. Clicking a mark on the canvas toggles Keep; clicking one on the tape highlights it on the chart. "Show me where this is" is not "I stand behind this", so they stay separate — and a canvas click also reveals the mark in the tape, scrolled into view, which is what closes the loop between the two surfaces.

The store is keyed by symbol and window, because a daily date names two different bars

A mark id is rule:date, and on a daily chart 2026-08-28 is the whole 23-hour Globex day in ETH and 09:30–16:15 New York in RTH. Measured against the shipped feed: over the 42 sessions the two windows share, 23 of the RTH daily chart's 53 marks carry an id an ETH daily mark also carries, and all 23 name bars whose OHLC differs — so one store for both meant a Keep made in one window silently landed on a different bar in the other.

markScope() appends the window slug for an aggregate only. Intraday keys already carry a time of day, so RTH and ETH there name the very same five-minute bar and rightly share a store; the feed's own daily series keeps the bare symbol, so every verdict already on disk is still found. RTH daily gets its own ES_F_rth.json.

mark up in the desktop app ↓ File → Export marks… data/marks.json tracked, like data/es_data.json ↓ npm run artifact dist/price_action_mark.html one file, no host, marks included

Publishing verdicts is what puts an artifact into confirmed-only mode. An artifact built with an empty data/marks.json shows every candidate; one built with verdicts opens on exactly the marks its author kept, while a viewer who switches back to all candidates keeps that choice locally.

That path is guarded at build time, because data/marks.json is a flat verdict map with no record of which window produced it. An RTH daily export dropped over the ETH daily snapshot published marks the author never confirmed, onto bars they never saw — verified end to end: three RTH verdicts produced a confirmed-only page showing three ETH bars, silently. inline-artifact.ts now compares the store's symbol against the snapshot's markScope and refuses the build. Only a store that carries verdicts is judged, so the shipped empty one still builds.

The settings maps are sparse, and sparse has two halves

settings.marks.rules stores only the ids the reader moved off the rule's own default. Persisting all 31 booleans would freeze today's defaults into every settings file, so a later tightening would never reach anyone who had already run the app.

Writing sparsely is only half of it: the merge has to delete too. toggleRule once only ever added, so a rule switched off and back on stayed pinned to today's answer for ever — exactly the failure the sparseness exists to prevent. It now drops a key whose value agrees with defaultOn, and the field-wise merge drops what an incoming record leaves out. marks.folded has always needed both halves, because taking a fold back is a key going away.

marks.show is sparse for the same reason, and it bit twice: a stored value has to mean "the viewer chose this", never "this was the default when they first loaded" — otherwise a first-time viewer sees every candidate instead of the author's marks, which is the one case the publish path exists for. marks.stopTarget follows the same rule and is stored only when it is off.

The same rules on both bar sizes

Daily and five-minute. The marking layer needed almost no change for the second one, and the reason is a single decision made early.

Dataset.d[i] is an opaque sortable string. A daily bar is 2026-08-28, an intraday one 2026-08-28T13:45:00Z. Both are ISO 8601, so < and > order them, a Map indexes them, markId(rule, at) keys a verdict on them, and the viewport test is untouched. Every consumer that treats a bar's date as a handle rather than a date needed no change at all: the rules, the canvas primitive, the mark store, the reading.

The dials are in bars, not days — pivot strength 3, BREAKOUT_LOOKBACK 20, ATR_PERIOD 20 — so they run on five-minute data unchanged, and the density transfers better than expected. Measured on a 60-day five-minute pull: a pivot every 6.7 bars against 6.8 on daily, and the same 0.71 marks a bar the daily defaults are budgeted to, so the budget still needs no second set of numbers. --check passes on that file too, including the no-lookahead test.

Inherited, not chosen

Nobody has swept --tune on intraday. The dials transfer and the density lands in the right place, but they were chosen against twenty-six years of daily bars and that is the only evidence there is for them. The golden fixture is daily and says so rather than reporting four failures that mean "wrong dataset": run against an intraday file it prints "fixture not compared: it holds the daily series" and checks nothing else.

The session window — RTH or ETH — filters the dataset rather than hiding bars on the chart, and that matters here more than anywhere. Metrics, structure, ATR, the rules and the readings all see RTH bars only; an RTH chart whose ATR was computed over the overnight is not an RTH chart. Measured: 11,609 bars become 3,402, 81 a session, every session, and --check passes on the filtered series. The consequence is that the bar before an open crosses the overnight and gap fires there, which is correct, and exactly how a daily series already behaves across a night.

Two things that look like details and are not. rolls is rebuilt, not remapped — the indices are positions in d, and dropping 71% of the bars moves every one of them. And rolls are a calendar fact, so the expiry arithmetic works off the day part of the key: contractStarts steps to the first bar of the next session, not i + 1, because five minutes after an expiry is still the expiring contract. On a daily series both reduce to exactly what they did before, and marks:check passing unchanged is what proves it.

How a detector gets tested

You cannot tune a wedge detector by squinting at a canvas: a rule that is subtly too loose looks exactly like one that is working.

  • Tune against the text oracle. npm run marks prints the same numbers the rules see, for any span — --rules, --catalogue, --trades, --structure, --read, --tune.
  • Pick the patterns by eye before writing the rule that finds them. It is the only way a detector is tested against something other than itself. The eight in data/marks-golden.json were read off the 2025 pivot list by hand; seven then matched the rule's own arithmetic exactly.
  • npm run marks:check is the regression guard. It holds the per-rule counts, those eight dates and the structure dials, and --golden rewrites it — deliberately a separate command, so drift has to be accepted on purpose.
  • Counts are compared only when the dataset fingerprint matches, because npm run data legitimately changes them. The hand-picked dates are history and are checked either way.

Verified to have teeth

Loosening BIG_ATR from 1.5 to 1.4 reports "big-bar: 450 marks in the fixture, 578 now", and tightening the double-top tolerance drops three of the eight hand-picked patterns. A guard nobody has watched fail is a guard nobody knows works.

--check has grown as the layer has, and each invariant is there because something broke it: the structure has no lookahead, every entry's walk starts at the date its own mark says it was knowable, every phrase in a reading is a rule that was knowable at that close, and mark ids are unique per rule. All four are shown failing above, in the section that introduced them — a guard nobody has watched fail is a guard nobody knows works.

That last one is the one a rule can break without trying. Two breakouts on consecutive sessions find the same first pullback, so bo-pullback once emitted two marks carrying one id: two identical rows, one verdict covering both, and a keyed {#each} that throws outright. Both rules now claim their signal bar, and detect() dedupes as a backstop — but the check runs per rule, since checking detect()'s output would only prove the backstop works.

What comes next is drawing

Detection is done, and so is the reading. What is left is marks the reader makes by hand — and everything it needs is already in place, built that way on purpose.

  • Mark already carries source: 'manual' and MarkStore already carries a manual array — but coerceStore() returns manual: [] unconditionally, on load and on save alike, so today the field is reserved rather than round-tripped. The serialised shape is already right and no file on disk needs migrating, which is the part that matters; the one function that has to change is coerceStore, and it has to validate what it lets through — a manual mark is the first thing in that file a reader could hand-edit into any shape.
  • MarkPrimitive.hitTest() already returns the id of whatever is under the cursor, which is the selection half of a drawing tool.
  • shapeOf is pure and consumed by both the renderer and the hit test, so a drag handle placed against one is placed against the other by construction.
  • The five geometry kinds — segment, channel, level, path, trade — all draw already. A tool has to produce one, not teach the renderer a new shape. path is the one nothing emits any more, since a double became a level; it is kept for the drawing tool, not left behind by accident.

Two things not to do when building it

Do not add a second canvas over the chart — attach to the candle series so drawings pan, zoom and hit-test in price/time for free. And do not persist rule output alongside the manual marks: it is derived, and storing it is how it goes stale against a refreshed dataset.
